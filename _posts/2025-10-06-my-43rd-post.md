## Overview

The fundamental flaw with a lot of Browser Based Detection and Response (BDR) tooling is that it can simply be disabled. There is nothing differentiating a BDR browser extension from a regular extension. There is no hierarchy of control as it is essentially an open plane. Endpoint Detection and Response (EDR) tooling in Linux/Windows environments are protected by a hierarchy, that being ring 0 to 4 or whatever, you get the idea. For the most part processes in userland are unable to interact with the kernel, thus protecting EDR drivers that live there and therefore, the functionality of the tooling. Whilst the browser has little controls, therefore, it is the wild west. This is fantastic for attackers but detrimental for startup companies trying to sell a vibe-coded BDR solution.

So to prove this theory, I created two tools:
1. **ExtensionExterminatorOS** (Exterminates from OS Level)
2. **ExtensionExterminatorJS** (Exterminates from Browser Level)

## Why would an attacker want to disable a BDR?
A malicious browser extension sitting on the Chrome or Edge store is useless if their is a BDR tool in the victims browser disabling it upon installation. So why not add some code to the malicious extension that disables the BDR tool itself?

Extensions have increasingly been used to facilitate C2 comms through the browser. APTs love extensions because most companies don't have a BDR solution and EDRs are blind to their activity. Mandiant have a great writeup on a sosphiticated custom malware suite that was using an extension to facilitate C2 comms through an extension.

## ExtensionExterminatorOS
Operational, however, very detectable, but clear text and readable for demo purposes. Load it with a AMSI bypass and bobs your uncle.

*High Level*
Adds an ``ExtensionInstallBlocklist`` to registry to disable extension(s) in Chrome and Edge.

*Requirements*
- Local Admin
- Windows Microslop Brickstation

*Limitations*
- Does not work for Firefox/Brave. These browsers use .xpi files for extensions and keep a handle on the file open for the entire time the browser is running that denies deletion. Therefore, for it to work, I'd have to kill Brave/Firefox, then exterminate the extension. Which is less realistic in a legitimate attack chain.
- Local administrator is required for the disabling of BDRs from the OS, for the most part.
- GPO/Intune policies can trigger to re-install these extensions.

*Logic*
1. Queries for installed browsers used on the host. Checks the reg entries ```HKCU:\SOFTWARE\Clients\StartMenuInternet"``` and ```HKLM:\SOFTWARE\WOW6432Node\Clients\StartMenuInternet```.
2. Queries for installed extensions on those browsers. Checks ```"C:\Users\*\AppData\Local\$($Info.UserData)\*\Extensions\*"``` for extensionIDs per browser.
3. Matches extension IDs with a kill list of IDs hardcoded into the script ```$Targets = Get-InstalledExtensions | Where-Object { $KillList -contains $_.Id }```
4. For each matched ID, writes the blocklist policy and deletes the external-install registrations. ```Add-ToBlocklist``` adds the ID to that browser's ```ExtensionInstallBlocklist``` registry policy, which disables it and stops it reinstalling. Then ```Get-ExtRegPaths``` builds the list of registry locations that can silently re-add an extension, HKLM, the 32-bit Wow6432Node variant, HKCU, and every logged-on user's hive under HKEY_USERS, and ```Remove-RegKey``` deletes each one that exists.
5. Deletes the on-disk extension folders. ```foreach ($t in $Group.Group) { Remove-Dir $t.Path }``` removes the actual extension files for every match, and because the inventory recorded one entry per user and per profile, this deletes the extension from all of them, not just the current user.

## ExtensionExterminatorJS
Who needs vulnerable drivers or novel AMSI bypasses to evade tooling when you can just write a few lines of .js instead.

*High Level*
Malicious extension that receives commands from a C2 to disable target extensions and then exfiltrate browser cookies and secrets.

*Requirements*
- Negligent employee who loves productivity hacks in the form of browser extensions

*Ponderings*
I tried to mimick a real attack chain for this, however, I ran into some obstacles. Windows does not allow installation of extensions through scripting for standard users, this is by design. However, administrative users can. So for the sake of this demo, I'll do this. However, in a real world scenario the user would have installed this extension from the Chrome/Edge store. The only way to mimick a realistic scenario is to upload my malicious extension on the Chrome/Edge store, which I am obviously not going to do. So that part of the attack chain is borked. Apologies.

Anyway I've added **ExtensionExterminatorJS** to a benign browser extension that I vibe coded in 30 seconds. It changes your Chrome background to black or green. For testing purposes I've published the extension and it's Flask Python HTTP Server config if you wish to re-create and build upon it in a home lab.

This demo demonstrates how you can send and receive commands from a C2 through an extension. I will flag that the extension is unable to receive code as such from C2, but can receive instructions. Therefore, all the nasty stuff has to live in the .JS of the extension when it is installed.

After spending too long looking at the Chrome API docs I ran into ``chrome.management.getAll`` which by definition "Retrieves an array of ExtensionInfo objects, one for each installed add-on." I use this API initially to determine installed extensions on the browser and exfil the dump via a HTTP POST request to my flask server at the endpoint /extensions.

My flask server then has a conditional statement that scans POST requests to this endpoint for target extension IDs such as "fjehgmfmkmgapgojgcfmgdempabonfdn" which is BrowserBuddy, my lightweight totally not shippable BDR tool. If there is a hit. It sends a response back to the extension with the instruction 'disableExtension' and the target extensionID.

Now how can an extension disable another extension? That is the burning question amirite? Chrome API docs strike again. ``chrome.management.setEnabled(id, false)``. Now this initially wasn't a home run as the documentation stated that it "may present the user with a native confirmation UI as a way of preventing abuse." However, I am yet to see a popup. So for me at least, this bloody works and it does so silently.

The caveat to this technique is ``ExtensionInstallForcelist`` which is a registry key that lives in ``Computer\HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Google\Chrome\ExtensionInstallForcelist``. When a browser extension is added to this forcelist it prevents ``chrome.management.setEnabled(id, false)`` from disabling it. For most organisations, they will push out extensions via Active DIrectory Group Policy or Intune which is done via this registry. However, if a company is pushing out extensions via a managed browser, the technique above still works.

My C2 is a handy flask server with some minor configs to add some functionality. I've added an endpoint at /extensions with a listener for those handy extension IDs that BackgroundJesus is sending. Once an extension ID is received it validates whether that extension ID is a ``TARGET_EXTENSION_ID``, if there is a match, it sends a request back to the extension to call the JS function ``disableExtension``. This is a JS function that lives in ``popup.js``. As far as I have tested the extension cannot receive JS to then run from my C2, my C2 can only invoke already existing JS to be ran. ## Summary
BDR solutions piece together the lack of visibility that EDRs have to browser-level processes/activity. Preventing all kinds of nasty attacks. However, it is important to remember that these solutions operate in the application layer, and thus the Chrome/Edge sandbox. Therefore, in my opinion they're fundamentally flawed. These providers are tool inside an application to extend it's functionality. The responsbility to prevent these browser-based attacks should be on Chrome and Edge, not a vibe coding extension developer. 

Whilst I think BDR solutions are absolutely necessary for enterprise environments looking to protect negligent users for the deep dark web, you need to be wary of what you're buying. That is a bolt on solution on top of a application.
