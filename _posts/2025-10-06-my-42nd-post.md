## Overview

Australian SMBs and mismanaged WordPress sites strike again. 

Over the past few weeks I've been looking at ways I can proactively hunt for *.com.au* sites delivering clickfix payloads. This has led me to many ideas... some far more feasible and legal than others. 

Whilst the other methods are a work in progress and are likely to take some time. I'll share my current way of doing it.

I'll also try to uncover the exact intrusion method for these infections. In attempt to directly attribute exploitation of a particular vulnerability to a cluster of compromised WordPress Websites.

This is a long writeup folks, buckle in.

### IOCs I am hunting for

The most common method for fetching Clickfix payloads once a user loads a site nowdays is through Ether Hiding. The method uses RPC calls to fetch heavily obfuscated JS code from smart contracts stored on blockchain testnets. This JS when obfuscated either contains the functionality
to present the Clickfix page to the user or makes a call to another domain that returns that code.

For the most part Etherhiding clickfix campagins usually pull payloads from one of four blockchain testnets:
1. publicnode.com
2. bnbchain.org
3. bscscan.com
4. drpc.org

On a real blockchain, you pay gas (small fee) for each time you fetch a smart contract. On testnets, this is free. Also by design with blockchains, you remove one link and the lot go down. Hence why they're used for nefariousness!

Anyway back on track. I want to be able to search for any website that is communicating with these blockchain testnets. Essentially any JS or HTML within a page that initiates a HTTP request or RPC call to any of these domains.

Now this is easier said than done for the following reasons:
1. No public tool scans every domain on the internet and records all domains it communicates too. There is tooling like publicwww however, after spending $50 on it I realised it's trash.
2. The JS embedded into infected websites that calls these domains is often different. Therefore, cannot perform a signature check by trying to match a string in the website's code.

### If money and the law wasn't a problem

In an ideal world, I'd do the following:
1. Pull a list of all .com.au domains from auDA
2. Run a python script to scan each websites page source for WordPress attributes 
3. Build a list of a Australian WordPress websites.
4. For each website submit a URLScan and dump all domains it communicates to (URLScan API).
5. If these domains match any known etherhiding domains write to a .txt and perform further domain enumeration.

This will work. The URLScan API successfully returns this info, I will demo this later. However, this is a very large recon job and will cost a lot of compute and money.
Particuarly the manual scanning of every .com.au for WP attributes as it will require indexing a lot of HTML. This is far out of reach for a lvl0socanalyst, but definitely not a nation state.

I know there are tools out there that already index Australian WordPress Websites..... But they cost money. A lot of it. The amount of queries I will need to make to determine this require a very expensive plans.

### Lightbulb moment - Introducing URLScan API

URLScan is an underrated database. When you submit a public scan for a website, it'll index the result. All the data from this result is then able to be queried for free using there API (capped at 100 results per call).

So. Why don't I query the URLScan historical database using the free API for the following conditions
1. *.com.au
2. Scanned within the last 30 days
3. Initiates a HTTP/RPC request to a blockchain testnet

It is unlikely a legitimate website is going to be communicating with these domains. Especially one that someone has already submitted to URLScan.

- MX, SPF, DMARC records
- Extensive WordPress fingerprinting (WordPress version, theme and plugins installed)
- VirusTotal rating
- Submits new scan to URLScan (Checks contacted domains against a known list of malicious etherhiding domains)
- All business data through Google Maps (Google Places API)

If you'd like to try and re-create this script here is some of the APIs it calls
- VirusTotal API
- IPInfo API
- Google Places API
- URLScan API
- Secret API

Running this script on the list of domains generated from above gives me the following:
- Extensive domain recon and business details
- Establishes whether malware is still on the site
- Records all plugins/themes/wp version and common misconfigs with WordPress
- Whether the site is already known malicious via reputation lookups

## Polygon Cluster ()

I have 35 domains communicating with these domains:
- ```polygon.drpc.org```
- ```megamegalodon.com```
- ```polygon-bor-rpc.publicnode.com```

This campaign uses a Polygon testnet to fetch payloads through etherhiding.

### Delivery Mechanism

The Clickfix delivery mechanism for this campaign is kind of novel. 

Firstly it sends an RPC eth_call request to the polygon address at two different domains:
- ```polygon.drpc.org``` =  (0x08207B087F61d7e95E441E15fd6d40BEfd6eD308)
- ```polygon-bor-rpc.publicnode.com``` = (0x08207B087F61d7e95E441E15fd6d40BEfd6eD308)

This RPC call returns the domain ```moll.lanjut.in```. A call to this domain is then made after some inline JS obfuscation to retrieve the malicious JS that serves the Clickfix prompt.

![Config](/images/secondary.PNG)

Interesting.... After a google or two the polygon address matches a VidarStealer campaign that is using the ErrTrafic ClickFix Bundle. I think we've found our campaign that ACSC has been warning us about. 
- [ACSC Vidar Stealer Alert - Targeting Australian WordPress Sites](https://www.cyber.gov.au/about-us/view-all-content/alerts-and-advisories/clickfix-distributing-vidar-stealer-via-wordpress-targeting-australian-infrastructure)

The unobfuscated JS and a bit of OSINT suggest that ErrTraffic is being used. This is a kit purchased for about $800 USD that gives users templates to use to deploy malware on compromised sites.

ErrTraffic is purely a delivery layer, it does not come with Vidar/Lumma or other infostealer stubs. It's essentially BYO malware. We'll provide a central panel to automate the deployment of the clickfix page and on the website you've compromised!

Yesterday, when I wrote ran my scripts ```megamegalodon.com``` had the same purpose as ```moll.lanjut.in```. Therefore, the threat actor is rotating this domain to avoid blocklists and reputational lookups preventing users from loading the JS stored there.

If you want to deep dive into how clickfix loaders work this older blog post of mine will do the trick. [Sosphisticated EtherHiding Delivery Mechanism](https://lvl0socanalyst.github.io/malware/analysis/2025/09/16/my-31st-post.html)

### Conclusions

So whilst all the advice out there currently about these campaigns is stating that vulnerable plugins and likely the intrusion method for these ether hiding campaigns my data set simply does not back that conclusion.

This insinuates vulnerable components as the only intrusion method. However, I can't back this up from my own analysis.

My hope was to find a clear vulnerability, but from my research it's obvious that multiple intrusion methods are being used.

In an ideal world, I'd have server-side logs to validate my conclusions.
