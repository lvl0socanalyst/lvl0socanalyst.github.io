## Overview

Australian SMBs and mismanaged WordPress sites strike again. 

Over the past few weeks I've been looking at ways I can proactively hunt for *.com.au* sites delivering clickfix payloads. This has led me to many ideas... some far more feasible and legal than others. 

Whilst the other methods are a work in progress and are likely to take some time. I'll share my current way of doing it.

I'll also try to uncover the exact intrusion method for these infections. In attempt to directly attribute exploitation of a particular vulnerability to a cluster of compromised WordPress Websites.

This is a long writeup folks, buckle in.

### IOCs I am hunting for

The most common method for fetching Clickfix payloads once a user loads a site nowdays is through Ether Hiding. The method uses RPC calls to fetch heavily obfuscated JS code from smart contracts stored on blockchain testnets. This JS when obfuscated either contains the functionality
to present the Clickfix page to the user or makes a call to another domain that returns that code.

For the most part Etherhiding clickfix campagins usually pull payloads from one of four blockchain testnets:
1. publicnode.com
2. bnbchain.org
3. bscscan.com
4. drpc.org

On a real blockchain, you pay gas (small fee) for each time you fetch a smart contract. On testnets, this is free. Also by design with blockchains, you remove one link and the lot go down. Hence why they're used for nefariousness!

Anyway back on track. I want to be able to search for any website that is communicating with these blockchain testnets. Essentially any JS or HTML within a page that initiates a HTTP request or RPC call to any of these domains.

Now this is easier said than done for the following reasons:
1. No public tool scans every domain on the internet and records all domains it communicates too. There is tooling like publicwww however, after spending $50 on it I realised it's trash.
2. The JS embedded into infected websites that calls these domains is often different. Therefore, cannot perform a signature check by trying to match a string in the website's code.

### If money and the law wasn't a problem

In an ideal world, I'd do the following:
1. Pull a list of all .com.au domains from auDA
2. Run a python script to scan each websites page source for WordPress attributes 
3. Build a list of a Australian WordPress websites.
4. For each website submit a URLScan and dump all domains it communicates to (URLScan API).
5. If these domains match any known etherhiding domains write to a .txt and perform further domain enumeration.

This will work. The URLScan API successfully returns this info, I will demo this later. However, this is a very large recon job and will cost a lot of compute and money.
Particuarly the manual scanning of every .com.au for WP attributes as it will require indexing a lot of HTML. This is far out of reach for a lvl0socanalyst, but definitely not a nation state.

I know there are tools out there that already index Australian WordPress Websites..... But they cost money. A lot of it. The amount of queries I will need to make to determine this require a very expensive plans.

### Lightbulb moment - Introducing URLScan API

URLScan is an underrated database. When you submit a public scan for a website, it'll index the result. All the data from this result is then able to be queried for free using there API (capped at 100 results per call).

So. Why don't I query the URLScan historical database using the free API for the following conditions
1. *.com.au
2. Scanned within the last 30 days
3. Initiates a HTTP/RPC request to a blockchain testnet

It is unlikely a legitimate website is going to be communicating with these domains. Especially one that someone has already submitted to URLScan.

### The secret sauce (script) - Further Recon

I won't be sharing this script because it took me far too long to write, it also may cross some boundaries that can be referred to as grey.

For each domain I feed into it, it returns and pipes to a .CSV:
- Site status (HTTP 200 or 403)
- Domain info
- DNS registrar
- MX, SPF, DMARC records
- Extensive WordPress fingerprinting (WordPress version, theme and plugins installed)
- VirusTotal rating
- Submits new scan to URLScan (Checks contacted domains against a known list of malicious etherhiding domains)
- All business data through Google Maps (Google Places API)

If you'd like to try and re-create this script here is some of the APIs it calls
- VirusTotal API
- IPInfo API
- Google Places API
- URLScan API
- Secret API

Running this script on the list of domains generated from above gives me the following:
- Extensive domain recon and business details
- Establishes whether malware is still on the site
- Records all plugins/themes/wp version and common misconfigs with WordPress
- Whether the site is already known malicious via reputation lookups

## Polygon Cluster (ErrTraffic)

I have 32 websites communicating with one of these domains:
- ```polygon.drpc.org```
- ```megamegalodon[.]click```
- ```polygon-bor-rpc.publicnode.com```

This campaign uses a Polygon testnet to fetch payloads through etherhiding.

![Config](/images/evalation.PNG)

### Delivery Mechanism

The Clickfix delivery mechanism for this deployment is standard. 

Firstly it sends an RPC eth_call request to the polygon address at two different domains:
- ```polygon.drpc.org``` =  (0x08207B087F61d7e95E441E15fd6d40BEfd6eD308)
- ```polygon-bor-rpc.publicnode.com``` = (0x08207B087F61d7e95E441E15fd6d40BEfd6eD308)

This RPC call returns the domain ```moll[.]lanjut[.]in```. A call to this domain is then made after some inline JS obfuscation to retrieve the malicious JS that serves the Clickfix prompt.

![Config](/images/secondary.PNG)

Interesting.... After a google or two the polygon address matches a VidarStealer campaign that is using the ErrTrafic ClickFix Bundle. I think we've found our campaign that ACSC has been warning us about. 
- [ACSC Vidar Stealer Alert - Targeting Australian WordPress Sites](https://www.cyber.gov.au/about-us/view-all-content/alerts-and-advisories/clickfix-distributing-vidar-stealer-via-wordpress-targeting-australian-infrastructure)

The unobfuscated JS and a bit of OSINT suggest that ErrTraffic is being used. This kit can be purchased for about $800 USD a month, giving subscribers templates to use to deploy clickfix on compromised sites.

ErrTraffic is purely a delivery layer, it does not come with Vidar/Lumma or other infostealer stubs. ErrTraffic provides a centralised panel to automate the deployment of clickfix pages on websites you've compromised, but BYO malware!

Yesterday, when I wrote ran my scripts ```megamegalodon[.]click``` was doing exactly what ```moll[.]lanjut[.]in``` is now. ```megamegalodon[.]click``` is now nowhere to be seen. Therefore, the threat actor is rotating this domain to avoid blocklists and reputational lookups preventing users from loading the JS stored there.

If you want an in-depth and technical report into Clickfix loaders this older blog post will do the trick. [Sosphisticated EtherHiding Delivery Mechanism](https://lvl0socanalyst.github.io/malware/analysis/2025/09/16/my-31st-post.html)

### Likely Intrusion Method?

94% of websites communicating with polygon-rpc.com have /wp-admin exposed and user enumeration is possible through /author (?author=1)
- This suggests /wp-admin bruteforcing and credential stuffing as a likely potential intrusion method.

There is no commonality in the plugins that these sites are using. 

## Campaign 2 (.shop)

I have 21 websites communicating with atleast one of of these domains:
- ```dnsnewtds[.]shop```
- ```dntds[.]shop```
- ```ntdnewtds[.]shop```

The landing page is slighly different from your standard CloudFlare Clickfix Lure!

![Config](/images/clicky.PNG)

### Delivery Mechanism

This delivery mechanism here is very different to the fellas using ErrTraffic.

On one infected website they've injected malicious JS into the theme ```factoryplus-child/js```. Therefore, when the page loads, by default WordPress loads this theme and the malicious JS is ran.

![Config](/images/malicious.PNG)

This JS contacts the ```.shop``` domain to fetch a secondary script that calls ```bsc-testnet-rpc.publicnode.com``` for smart contract address that then returns the Clickfix JS.

Smart contract address:
- ```0xA1decFB75C8C0CA28C10517ce56B710baf727d2e```

Each website I've looked at from my data set that is communicating with one of the ```.shop``` domains has the JS injected in a different spot. Furthermore, is obfuscated completely different, however, returns the exact same smart contract.

For example another website has injected into the theme ```hello-elementor``` however, in a different subfolder and in a different way

![Config](/images/web2.PNG)

### Likely Intrusion Method?

The three domains above have all historically have resolved to ```178[.]16[.]53[.]137```

Validin has 32 domains that currently or historically have resolved to this IP. Lots of ```.shop``` domains following the same pattern.

OSINT suggests the domains that have resolved to ```178[.]16[.]53[.]137``` have been attributed to fake WordPress plugins. However, of the WordPress sites I have that communicate with ```.shop``` there are only few with suspicious plugins.

This is fascinating because it is not an angle I thought about exploring as an intrusion method.

Scanning through the websites from my data set that communicate with ```.shop``` domains, none have fake plugins. However, my method for detecting installed plugins is susceptible to oversight here as it is not validating the legitimacy of the JS the plugins use.
Therefore, you could name a plugin "Elementor-Pro 4.1.1" and have it show up as that in my results.

After piping through the data further there is no vulnerable plugins sticking out with high severity CVEs that could result in direct unauth'd JS injection/RCE.

### Web developer compromise perhaps?

In threat intel reports you often see web dev compromises causing mass WordPress infections. So I attempt to check this for my list of sites, just to be sure I haven't missed a plausible intrusion angle.

For all 53 infected websites I legally index the page source and search for email addresses using python ```requests``` and a bitta regex.

![Config](/images/regex.PNG)

I have a lot of FPs here, about 1000 entires. After manually deleting the excess I'm left with about 70 emails scraped from the page source.

To query whether these emails have been popped I'm querying the Hudson Rock API. They have a free API that maintains an updated list of accounts that have shown up in infostealer logs.

Here's the script if you're interested.

[Hudson Rock Compromised Account Checker](https://github.com/lvl0socanalyst/Scripts/blob/main/hudsonrock_infostealer_log_api.py)

Just querying the Hudson Rock API is missing a few angles on how a developer could be compromised. However, nowdays infostealers seem the most likely. Traditional targeted phishing campaigns are becoming extinct and data breaches that leak clear text creds even more so.
Well unfortunately, from 70 emails scraped, no hits.

### Conclusions

So whilst the current advice is stating that vulnerable plugins are the likely the intrusion method for Clickfix campaigns targeting Australian SMBs my data set does not support that.

My hope was to find one singular vulnerability, but from my research it's obvious that multiple intrusion methods are being used.

In an ideal world, I'd have server-side logs to validate my conclusions here. Without server-side logs the analysis I can do is limited.
